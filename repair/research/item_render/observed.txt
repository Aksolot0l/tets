This is an offline file scan, not runtime data. Candidate RTTI names:
  ItemInHandRenderer substring RVA 0x0186352c
  ItemRenderer substring RVA 0x01862c94 (also other substrings)
The string diamond_sword is at RVA 0x011eab78. A code reference at
0x00aa8d14 is inside a function beginning at 0x00aa8ce0 that passes this
string to a constructor/helper and stores a returned pointer in an indexed
global table. It looks like item registration; no rendering semantics, item
identity ABI, calling convention or safe interception point are proven.
The iteminhand strings at 0x011e8a40 are referenced from code around
0x00a32ae3 and 0x00a32d1b, likely name/data lookup, but this is unverified.

Do not hook, replace, suppress, or replay any draw on the basis of these
strings and candidate windows. Follow-up RTTI file scan may identify vtables
and candidate method bodies, but only targeted runtime observation can establish
whether a function corresponds to held items and which stack is a diamond sword.

Existing player-render diagnostics contain a direct call at 0x56cd2a to
0x5a22f0 with the fourth argument in R9, followed by calls at 0x56cd4c and
0x56cd89 to 0x59f2c0/0x59f200 and candidate tessellator operations. At
0x5a22f0, the fourth argument's +0x10/+0x18 pointers and apparent renderer
state lead into tessellator setup. A helper at 0x5a23f0 reads a +0x10 item
pointer and its +0x36 short field; registration at 0xaa8d2b also reads that
field. This is a candidate identity relationship only: no stack layout,
first-person path, diamond identity, thread affinity, transform or safe
suppression behavior is confirmed. Do not skip/call/hook these functions on
this evidence alone; the code can modify renderer/tessellator state.

User-supplied ITEM_RENDER_DIAG_3.txt, same executable SHA. In candidate
0x59f300 the third parameter is used as an item-stack-like object, with
pointers at +0x10/+0x18. Code in 0x5a10a5 likewise selects that object's
+0x10 pointer and reads a short at +0x36; this resembles the field used by the
item registration sequence. 0x59f200 is not a no-side-effect draw: it calls
0x7308c0/0x730bd0/0x730cd0 based on flags in its second parameter. Skipping or
replacing it based only on a file scan could break setup/cleanup and hand or
other item draws. 0x509640 is arithmetic on floats/shorts, not verified item
identity. Which path corresponds to first-person diamond sword, where to place
custom geometry and whether the current material honors colors remain unknown.

The supplied katana contains 4572 vertices, 7866 triangle indices and five
materials; no images, skinning or animation. The offline converter produces a
bounded GCM1 model retaining positions, normals and base colors. This is only
asset preparation; GCM1 is not yet loaded or displayed by the game client.

Further offline analysis (no new runtime report): at 0x59fcb1 the candidate
stack saved from the third parameter of 0x59f300 is passed in R9 to 0x5a22f0,
followed by a call to tessellator method 0x5d1790. Inside 0x5a22f0 one branch
calls the known tessellator begin at 0x5d0660 and another calls 0x5a0de0. This
is evidence of geometry preparation, not proof that replacing the function is
safe. The alternate branch at 0x59fcf6 bypasses it and calls 0x59f200 instead;
a hook there would not automatically cover all render paths. Material and
state setup occurs before this sequence, while cleanup follows it. The exact
meaning of parameters, mode, vertex layout and color/material binding remain
unverified. Do not ship a render hook from this observation alone.

The sequence 0xaa8d14-0xaa8d4a associates the diamond_sword string with an item
pointer and places it in the array at 0x190afa0, indexed by a signed short read
from item +0x36. Independently, published 1.1.0.1 Win10/MCPE item ID listings
identify diamond_sword as 276 (https://gist.github.com/jocopa3/f8c9f9158ede0e9d057781188ba440f5).
A mock-tested, unused candidate check in src/diamond_sword_candidate.h requires
a stack's active byte, candidate item pointer, 276 field and matching registry
slot simultaneously. 1.1.0.1 documentation is not runtime proof for this exact
1.1.5 build, nor does the check establish which player or render pass is active.

Subsequent opt-in experiment: the built DLL now tries the one direct
0x5a1d28 -> 0x59f300 -> 0x59fd19 -> 0x59f200 first-person chain. It uses
candidate identity, same local player, expected return addresses, validated
EXE/prologues, idle tessellator and same GPU context. After a custom GPU draw
is observed it runs the original CPU method while suppressing that method's
GPU draws, and falls back to the original if preparation fails. This is NOT a
proof of visibility, ABI, safe render state, shader/material or hand placement;
Windows game testing remains mandatory. The alternative branch and third person
are unimplemented. Switch is off by default and this note supersedes earlier
historical statements that these components are not connected to the DLL.
