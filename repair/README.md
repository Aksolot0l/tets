# Экспериментальное восстановление

Адаптер содержит отсутствующую точку запуска: подключает DX11 Present/Present1,
инициализирует рендерер ImGui и UWP-ввод, а также ограничивает обновление ввода
одним вызовом за кадр. Сам интерфейс остаётся в исходной DLL.

В обновлении: координаты мыши переводятся в клиентскую область окна (если
Win32-вызовы разрешены), добавлен встроенный шрифт с кириллицей, размер шрифта
увеличен до 16 px, начальный масштаб интерфейса — 1.20. Сохранённый профиль
может переопределить масштаб; в таком случае измените Settings → UI Scale.
На пользовательском скриншоте кириллица и масштаб 1.20 отображаются. Прокрутка колёсиком в игре пользователем подтверждена; положение курсора после исправления в игре остаётся непроверенным.

**Это не проверенная на Windows сборка.** Не подтверждено, что она работает в
Minecraft, на какой версии игры, с каким рендерером, мышью и масштабированием.
Есть риск зависания или закрытия игры. DirectX 12 не поддерживается. Не
устанавливайте её поверх работающих файлов; перед испытанием сохраните данные.

Для ручной проверки используйте `repair/client.exe` и положите рядом:
- `repair/GAYClientLauncher.dll` как `GAYClientLauncher.dll` (нужна для старта EXE);
- `repair/GAYClientInternal.dll` как `GAYClientInternal.dll`;
- исходную DLL из корня репозитория как `GAYClientCore.dll`.

При необходимости `ENABLE_ACCESS.cmd` в этой папке отдельно открывает чтение и
выполнение для ALL APPLICATION PACKAGES обоим DLL. Перед этим он сохраняет
исходные права; `RESTORE_ACCESS.cmd` возвращает их. Эти скрипты не проверялись
на Windows. Инжектору может потребоваться выбрать новую DLL вручную.

Адаптер привязан к исходной DLL SHA-256
`f74a42c4aedd1c9d1f0c92200e9c7e977d800ab686d108114b2711c0c81835c5` и ImGui
1.91.9b. Исходный файл не соответствует старым контрольным суммам README и
SHA256SUMS.txt. Не следует считать вычисленный хеш подтверждением доверенности.
Адаптер оставляет DX11-хуки установленными до закрытия процесса; выгрузка без
перезапуска игры не поддерживается. Лог ошибок выводится в OutputDebugString с
префиксом `GAYClient repair:`.

Используемый файл заголовка Dear ImGui 1.91.9b и его MIT-лицензия находятся в
`vendor/imgui`. Все вызовы интерфейса выполняются из старой DLL; второй экземпляр
ImGui в адаптер не включается. Для чтения и записи профилей используется
nlohmann/json 3.11.3, лицензия MIT находится в `vendor/json/LICENSE.MIT`.

Установка и обновление: `INSTALL_FROM_GITHUB.ps1` в корне проекта. Он скачивает
свежий манифест и выбранные файлы из ветки, обновляет распознанные предыдущие
версии на месте и сохраняет локальные резервные копии ACL. Проверка SHA-256
относительно манифеста из той же ветки не является независимой проверкой
подлинности. При выпуске новой версии добавляйте старый хеш изменённого файла
в `previousSha256` и обновляйте `size` и `sha256` в `install-manifest.json`.
Новый установщик не проверен на Windows.

## React-интерфейс в клиенте (эксперимент)

Дизайн из ZIP встроен в `GAYClientLauncher.dll` как локальный HTML и открывается
в WebView2 внутри того же `client.exe`. Интернет для самого интерфейса не нужен.
Нужны установленный Microsoft Edge WebView2 Runtime и `WebView2Loader.dll` рядом
с EXE. Если WebView2 не запустится или процесс интерфейса завершится с ошибкой,
лаунчер покажет предупреждение и вернётся к предыдущему встроенному окну.
На реальной Windows/WebView2 этот вариант пока не проверен.

Кнопка запуска вызывает прежнюю нативную активацию выбранного App ID, статусы
поступают от реального потока автозагрузки. `DLL загружена` означает только
загрузку библиотеки, не подтверждение работы оверлея. Поиск определяет App ID из
единственного запущенного `Minecraft.Windows.exe`; профили читаются из прежнего
нативного хранилища и сохраняются атомарно. Профильный ник - заметка, не аккаунт.
Параметры оформления хранятся в локальном хранилище WebView2. Фиктивный каталог
модов и статистика из макета отключены и заменены пояснением, что функций пока нет.
Независимые окна/ники, автопроверка обновлений и трей не реализованы.

HTML доступен WebView2 только через перехваченный локальный адрес; остальные
запросы и навигация блокируются, доступ JS к нативным действиям ограничен
белым списком команд. Это эксперимент и не заменяет проверку безопасности.
Установщик проверяет подписанный Microsoft `WebView2Loader.dll` через
`Get-AuthenticodeSignature` до замены файлов. Заголовок и DLL взяты из пакета
Microsoft.Web.WebView2 1.0.2651.64 (SHA-256 nupkg
`c7909cdab68a56d1b8eeb1d5b18b0e00122ed812a075a8be785ed48de689eeca`),
полученного из публичного GitHub-зеркала `winsoft666/QWebView`; проверка
подписи на целевой Windows обязательна. Лицензии в `THIRD_PARTY_NOTICES.txt`
и `vendor/webview2`.

## UWP-ввод и автоматический запуск (эксперимент)

Адаптер подключает обработчик `PointerWheelChanged` на диспетчере CoreWindow,
передаёт дельту колеса в ImGui и пытается учесть происхождение клиентской области
CoreWindow при пересчёте курсора. Падение обратно на старый ввод предусмотрено,
если данные окна недоступны. Эти изменения собраны и прошли статические тесты,
но не проверены в Minecraft на Windows; нельзя гарантировать, что игра доставит
события или что окно возвращает нужную систему координат.

Теперь устанавливается один EXE — `client.exe`. Его оригинальный код не
изменён; для точно проверенного исходного EXE добавлена секция PE-импорта
`GAYClientLauncher.dll`. DLL показывает новое окно лаунчера и запускает поток
автозагрузки **внутри процесса клиента**, без второго EXE и консольного окна.
После создания нового окна исходный интерфейс скрывается. Если новое окно не
создастся, исходный интерфейс остаётся доступен. Аварийный переход на старый
интерфейс: закройте клиент и создайте пустой файл `launcher-classic.flag` рядом
с EXE; для возврата к новому окну удалите только этот файл. Оставьте DLL
загрузчика и обе DLL оверлея рядом с EXE.

Новая вкладка «Профили» позволяет создавать, удалять и выбирать локальные
профили. При первом запуске выполняется импорт локальных профилей и выбранного
App ID из `%LOCALAPPDATA%\AogiriGreenLauncher\settings.json`; исходный файл не
изменяется. Новые данные сохраняются отдельно в
`%LOCALAPPDATA%\GAYClientLauncher\profiles.json`. Если существующий файл нельзя
прочитать, сохранение блокируется, чтобы не затереть данные. Ник здесь — только
заметка и не изменяет ник или учётную запись в Minecraft. Автоматическая смена
аккаунтов и запуск нескольких окон с разными никами не реализованы.

Кнопка «Начать игру» отправляет запрос для App ID выбранного профиля, а не для
жёстко заданного пакета. Если ID не импортировался или больше не работает,
запустите одно окно Minecraft через меню «Пуск», перейдите в «Профили», нажмите
«Найти игру», затем «Сохранить». Закройте игру перед испытанием кнопки запуска.
Загрузчик ожидает ровно один процесс `Minecraft.Windows.exe` и через 10 секунд пытается автоматически
загрузить `GAYClientInternal.dll`. После того как обнаруженная игра завершится,
лаунчер автоматически закрывается (также если игру открыли через меню «Пуск»).
Ожидается сигнал завершения конкретного процесса и проверяется, что других окон
Minecraft нет; при невозможности открыть процесс используются три последовательных
успешных снимка списка процессов. Ошибку получения списка за закрытие игры не
принимаем. Лаунчер не закрывается сам, если игра ещё ни разу не была обнаружена.
При закрытии окна лаунчер сначала запрашивает обычное завершение и, если старый
код продолжает работать, через три секунды завершает только собственный процесс.
Эта логика пока не испытана на Windows; при непредвиденной ошибке прав доступа к
процессу или перечисления процессов автозакрытие может не сработать. Для новой
игровой сессии снова запустите `client.exe`. Несколько игр не поддерживаются.

Статус «DLL загружена» подтверждает лишь
загрузку файла, а не успешную инициализацию оверлея. Оставляйте лаунчер открытым,
пока нужна прокрутка. Закрытие лаунчера завершает его потоки. Новое окно и запуск
приложения не проверены в реальной Windows; нужна проверка пользователем.
Окно лаунчера можно разворачивать и менять его размер: при изменении размера
пересчитываются размещение и размеры карточек и элементов профилей. Поддержка
DPI и разворачивание требуют проверки на реальной Windows.
Главная страница использует созданную ИИ иллюстрацию из
`repair/assets/launcher-world.jpg` и маскота, предоставленного пользователем,
из `repair/assets/mascot.png`. Иконка окна создана из этого маскота и хранится
в `repair/assets/mascot.ico`. Ресурсы встроены в DLL и не требуют отдельных
файлов в папке установки. Для рисования используется системная библиотека
Windows GDI+. При ошибке загрузки изображений интерфейс остаётся работоспособным
и показывает запасное оформление. Изображение маскота пока добавлено только в
лаунчер и его окно, не в игровой HUD.

При обновлении установщик удалит только известные неизменённые версии прежнего
`START_CLIENT.exe`; файл с неизвестным хешем будет сохранён. При ошибке появится
окно, а подробности (в том числе PID) будут в `client-autoload.log` рядом с EXE,
если запись разрешена. Новая PE-сборка и автозагрузка не проверены в реальной
Windows/Minecraft, поэтому работа кнопки и DLL требует проверки. Это не отменяет
ограничения и возможных проблем с прокруткой, курсором и координатами.

В качестве экспериментального обхода отсутствующих событий колеса добавлены
PageUp и PageDown: при открытом меню наведите указатель на длинную вкладку и
нажимайте или удерживайте эти клавиши. Они запрашиваются из существующего UWP
опроса клавиш и преобразуются в события прокрутки ImGui; нажатия не записываются
в лог. При неверном положении указателя или если игра не передаст эти клавиши
способ также может не сработать. Это не подтверждённое исправление колеса мыши:
проверка в игре необходима.

## Новая экспериментальная прокрутка и координаты 1.1.5

Загрузчик в клиенте дополнительно устанавливает системный `WH_MOUSE_LL` hook.
Он пропускает все события дальше и сохраняет только дельты колеса, когда окно
Minecraft является активным; клавиатура, клики, движения курсора и другие окна
не записываются. Через анонимную область памяти и продублированный read-only
handle дельты передаются в адаптер внутри Minecraft. На диск эти данные не
записываются. Когда клиент закрывается, Windows убирает hook. Если мост не
создан, сохраняется UWP-обработчик. В `client-autoload.log` есть состояние
создания и подключения моста, но не история событий. Это ещё не проверено в
Windows и не гарантирует корректную прокрутку на конкретной системе.

В открытом меню есть переключатель `Coordinates (test)`. Адаптер внутри игры
пытается прочитать значения из памяти **Minecraft Windows 10 1.1.5 x64** по
опубликованным для неё указателям. Доступ только на чтение; перед использованием
проверяются имя процесса, PE timestamp `5976da7b`, тип PE, границы и согласование
двух путей высоты. При любой ошибке отображается `XYZ: not ready` или
`XYZ: unsupported game build`, старые значения не удерживаются. Это лишь
эвристики, а не гарантия, что память указывает на нужного игрока: при первом
испытании в мире нужно сравнить значения с независимо известными координатами,
например выводом доступной игровой команды, и убедиться, что они меняются при
движении. HUD отображает целые координаты блоков: округление вниз (в том
числе для отрицательных X/Z), а от целой Y дополнительно вычитается один блок
по наблюдению пользователя. Это поправка отображения, которую нужно проверить
в игре, а не доказанная модель высоты игрока. Диагностика пользователя показала, что альтернативная цепочка C
читается и её Y согласуется с независимой цепочкой B; идентичность и точность
всех трёх координат пока не подтверждены в игре. В главном меню корректного
игрока/мира может не быть.

Независимые публичные источники, на которые ориентировались при исследовании
смещений: [таблица для 1.1.5, сохранённая в истории проекта](https://github.com/Willemere/Cheat-Engine-Table-for-Minecraft-Windows-10-Edition-v1.1.5/tree/747541cd1279d7fe71a396ff28773ee4b88cd909)
и [Octopus Client для 1.1.5](https://github.com/Willemere/Octopus-Client).
Они сами по себе не доказывают корректность для конкретного бинарника игры.

Если в открытом мире написано `XYZ: not ready`, воспользуйтесь
`repair/DIAG_COORDS.ps1` из репозитория, не закрывая игру. Это отдельная
диагностика, не часть установщика: она открывает единственный Minecraft-процесс
только для чтения и проверяет три конкретные цепочки указателей. В консоль
выводятся только признаки доступности и согласованности; координаты, адреса,
фрагменты памяти и личные данные не выводятся, не сохраняются и не отправляются.
Никакие данные игры не изменяются. Скрипт требует Windows PowerShell и не
проверен в реальной Windows. Диагностические метки не означают, что найденные
значения действительно относятся к игроку.

Сборка адаптера и встроенного загрузчика (Zig C++; проверено на 0.17.1 из pip
`ziglang`), затем воспроизводимое создание EXE из точного исходного файла:

```
python3 repair/tools/build_adapter.py
cd repair/launcher-web
npm ci --ignore-scripts
npx tsc --noEmit
npm run build
cd ../..
zig rc /fo repair/launcher_ui.res repair/src/launcher_ui.rc
zig c++ -target x86_64-windows-gnu -std=c++17 -shared -O2 repair/src/client_autoload.cpp repair/src/launcher_ui.cpp repair/src/launcher_webview.cpp repair/src/launcher_profiles_win.cpp repair/launcher_ui.res -o repair/GAYClientLauncher.dll -luser32 -lgdi32 -lshell32 -lshlwapi -lole32 -lgdiplus -luuid
python3 repair/src/patch_client.py
```

## Дизайн-палитра лаунчера в игре (RCSS v3)

Внутриигровое меню переведено на палитру веб-лаунчера: акцент `#3ae882` ->
`#6ef58c` (+ `#c4ff62` strong / `#2fa960` deep), приглушённые тексты
`#89a792`/`#5f7a68`, тёмная база `#06110b`. Фирменные градиенты лаунчера
добавлены через `decorator: linear-gradient(...)` (в RmlUi 6.3 градиенты —
это свойство decorator, рендерятся через CompileShader/RenderShader, которые
DX11-рендерер реализует): шелл 160deg, зелёная кнопка 180deg
`#c4ff62 -> #6ef58c -> #2fa960`, активный пункт навигации 90deg, трек
включённого тумблера 90deg, карточки и окно Test tools. Градиенты
верифицированы попиксельно в софт-растеризаторе (репро в /tmp, см. историю
коммитов): углы шелла остаются скруглёнными, раскладка не изменилась,
плоские цвета — fallback через background-color.

## Внутриигровое меню: два окна (v6)

Меню в игре — ровно два окна в дизайн-системе лаунчера: **Home** (модули +
кнопка HUD-редактора) и **Visuals** (выключатель 3D-превью и все настройки
эффектов сворачиваемыми секциями China Hat / След / Кольца прыжка / Катана;
внизу секции катаны — её диагностика). Отдельные окна эффектов и окно короны
ликвидированы, корона из интерфейса убрана совсем. Каждое окно:

- перетаскивается за заголовок (RmlUi drag-события), не уезжает за экран;
- сворачивается в заголовок кнопкой «-»/«+» в углу (ASCII-глифы: U+25BE в
  Segoe UI превращается в «0»);
- прокручивается колесом мыши внутри себя, направление исправлено на
  привычное (знак wheelY инвертируется при передаче в RmlUi);
- поднимается наверх кликом (z-index + подсветка активного окна).

v6 по сравнению с v5:

- тумблеры заменены квадратными чекбоксами: пустой квадрат, когда выключено,
  галочка (рамка из двух линий, повёрнутая на -45°), когда включено;
- убраны дублирующие выключатели эффектов вверху окна Visuals — у каждого
  эффекта один выключатель внутри его секции; приписки у заголовков секций
  (jump, trail, конус, katana) убраны;
- анимированные RCSS-иконки модулей удалены полностью (признаны
  нейрослопом): строки модулей — обычные текстовые строки с чекбоксом;
- типографика обычная: без точек-разделителей «·», тире заменены на дефис;
- плавные анимации везде: показ/скрытие меню затемняет весь документ (класс
  `body.faded` + transition), секции сворачиваются анимацией max-height /
  padding / opacity, окна сворачиваются интерполяцией высоты на C++ (150 мс,
  ease-out) — inline `SetProperty` в RmlUi переходы не запускает, поэтому
  фейд идёт через класс, а высота — из C++;
- закрытие крестиком или Esc всегда возвращает игру в нормальный режим:
  адаптер принудительно сбрасывает флаг меню клиента (runtime+0x551), чем
  исправлен баг «после закрытия интерфейса пропали хотбар, старт-меню и
  кнопки серверов» (клиент сбрасывает флаг только своим RShift, из-за чего
  игра оставалась в мёртвом режиме меню);
- интерфейс уменьшен вдвое относительно v5: зум
  clamp(max(H/1080, W/1920)·0.625, 0.575, 1.0), т.е. 0.625 на 1080p.

Весь интерфейс масштабируется под разрешение: каждый `px` в RCSS умножается
на UI-зум при загрузке, константы раскладки — тем же коэффициентом.

Раскладка по умолчанию вычисляется из размера экрана (menu_layout.h, чистая
функция — тот же код проверяется пиксельным харнессом на Linux): окна
упаковываются в ряды по ширине, ряды центрируются и пропорционально сжимаются
по высоте; пока включено 3D-превью, справа резервируется полоса под него.
Кнопка «Сбросить раскладку» в окне Home возвращает всё на места. Проверено
попиксельно (repro6): раскладка без пересечений, половинный зум, чекбоксы
(галочка рендерится), анимации секций и окон, фейд документа, знак колеса,
полоса превью.

## Редактор HUD и 3D-превью (v5, уточнён в v6)

Кнопка «Настроить HUD» теперь скрывает вообще всё, кроме самого HUD: игрок
видит живые виджеты и перетаскивает их мышкой, внизу — одна строка подсказки
(«HUD EDIT - перетаскивай элементы мышкой - Esc - выход»). Никаких колонок и
тулбаров. Технически: пока редактор открыт, `patchedDrawHud` продолжает
рисовать HUD, а уже установленный хук `ImGui::Begin` (themedBegin) для
каждого HUD-окна («##hud_*», «##module_hud»):

- подменяет прибитую игрой позицию на пользовательскую (`SetNextWindowPos`
  сразу перед `Begin` побеждает предыдущий вызов игры);
- снимает точный прямоугольник через экспортируемые `ImGui::GetWindowPos` /
  `GetWindowSize` и рисует акцентную рамку;
- двигает окно за мышью (сэмпл UWP-указателя из адаптера + зажатая ЛКМ),
  не давая утащить виджет за экран.

Позиции живут одну сессию и не трогают профиль игры. Выход — Esc: начиная
с v6 адаптер гарантированно сбрасывает флаг меню клиента при выходе из
редактора (раньше флаг оставался установленным и игра зависала в режиме
меню). Повторное открытие меню — правый Shift.

«3D превью» в окне Visuals включает портрет игрока: окно без рамки у правого
кромки экрана рисуется в игровом ImGui-проходе (`drawRmlVisualPreview`,
проверенная механика скина/аватара из старого редактора — живые параметры
China Hat или следа), а RmlUi-окна рисуются позже и всегда сверху.

## Диагностика мыши и Del

Для известного исходного `GAYClientCore.dll` адаптер до установки графических
перехватов проверяет PE, точный участок машинного кода, экспорт Present и
формат строки, а затем меняет только шесть байт в памяти процесса, обходя блок
отрисовки UWP mouse test вместе с его фоном. Исходная DLL на диске не меняется.
При несовпадении или ошибке защиты памяти изменение пропускается и причина
выводится в OutputDebugString. Это относится исключительно к известной сборке;
в Windows требуется отдельная проверка.

При активном окне Minecraft нажатие **Del** останавливает отрисовку оверлея и
обработку дополнительного ввода мыши внутри адаптера. Отдельный мост колеса
в лаунчере остаётся работать до выхода из игры. Del, удерживаемый при
переключении окна, не считается новым нажатием; при вводе в поле ImGui он не отключает оверлей. Для повторного
включения нужно закрыть и заново запустить игру. Это **не физическая выгрузка**:
DLL, DX11-перехваты и обработчики WinRT остаются в процессе до его закрытия.
Удаление закреплённого модуля с активными обратными вызовами опасно, а исходников
старого ядра и полного механизма его безопасной очистки в репозитории нет.
Клавиша и отключение экспериментальные и требуют проверки в игре на Windows.

## Загрузка нового интерфейса

Пока запускается WebView2, окно показывает заставку загрузки вместо старой
Win32-страницы. Если WebView2 не запустился, сработал тайм-аут или его процесс
аварийно завершился, остаётся доступен резервный Win32-интерфейс. Исходное окно
старого EXE скрывается сразу после появления окна лаунчера и проверяется снова
каждые 125 мс; до создания нового окна краткое появление исходного окна всё ещё
возможно. На Windows порядок появления и обработка ошибок требуют проверки.

## Встроенное новое меню GAYClient на RmlUi (HTML/CSS)

Игровое меню полностью переделано на RmlUi и встроено в адаптер модулями
`src/menu_rml.h/.cpp` (мост) и `src/menu_rml_data.h` (весь дизайн: два RCSS
и два RML-документа в виде raw-string массивов). Прежнее ImGui-меню
(`menu_embed` + `GAYClientMenu`) из сборки удалено; легаси-интерфейс остаётся
автоматическим фолбэком на случай сбоя инициализации RmlUi.

- меню рисуется в конце Present-пути, после оверлея легаси, собственным
  RmlUi-контекстом `RenderInterface_DX11` на том же устройстве: адаптер
  создаёт render target view бэкбуфера и передаёт его в
  `menu_rml::RenderOverlay(device, rtv, w, h)`; рендерер сам биндит таргет
  в `EndFrame` и восстанавливает всё изменённое состояние D3D11, Present-путь
  игры не затрагивается;
- ввод берётся только из существующих перехватов: курсор — из `patchedPointer`
  (DIP→px тем же способом, что раньше), колесо — из того же сэмпла UWP (одна
  единица на щелчок), клавиши — из экспорта `UwpKeyDown`. Кнопки мыши и Escape
  пересылаются только по переходам (RmlUi обрабатывает каждый вызов как новое
  событие). Новых игровых хуков нет;
- шрифты — системные Segoe UI / Segoe UI Semibold (`C:/Windows/Fonts`),
  читаются в память один раз и регистрируются через `Rml::LoadFontFace`
  (семейство `GAY`, буферы живут всё время работы DLL); кириллица включена;
  если шрифты не найдены — инициализация честно не удаётся, работает фолбэк;
- включение/выключение модулей — только через существующие проверенные
  сеттеры: China Hat / Trail / Jump Rings / Katana / 3D crown — напрямую,
  HUD-модули (FPS, CPS, Clock, Keystrokes, Watermark, Coordinates, Resolution,
  CPU/RAM, список модулей) — через очередь, которую `patchedDrawGui` исполняет
  на своём потоке через `ag::Runtime::SetModule`. Флаги HUD-модулей меню
  держит в собственной «тени» (однократный стартовый снимок живого состояния),
  иначе живое чтение состязалось с очередью и тумблер «отщёлкивался» обратно;
- дизайн в стиле лаунчера: shell 1140x716 с клампом от размеров вьюпорта,
  левый нав-рейл, вкладки Модули/Графика/HUD/Инфо, карточки-строки модулей с
  тумблерами (button.switch + span.knob с CSS-переходами), сворачиваемые
  секции China Hat/Trail/Кольца/Катана/Корона («типо вкладки»), слайдеры
  `input[type=range]` со стилизованными slidertrack/sliderbar и живыми
  значениями, чипы цвета RGB, крупный базовый шрифт 20px, акцент #3ae882,
  скроллбары и hover-анимации на CSS-переходах;

### RCSS-грабли RmlUi 6.x (почему однажды были видны только ползунки)

Вид «только ползунки» на первом кадре был воспроизведён и вылечен в
софт-растеризаторе на Linux (сборка ядра RmlUi + FreeType без GPU, покадровый
дамп в BMP). Три независимые причины, все — особенности RCSS, а не DX11:

1. **`rgba(r,g,b,a)` с дробной альфой невидим.** Парсер `PropertyParserColour`
   читает компоненты через `atoi`, поэтому `rgba(10,16,13,0.97)` даёт альфу 0.
   Все полупрозрачные цвета в `menu_rml_data.h` записаны как `#rrggbbaa`.
2. **Дефолтный `display` в RmlUi — `inline`** (у него нет дефолтного
   user-agent-стилей для div). Блочные контейнеры (карточки, секции, обёртки
   текста) без явного `display: block` ссыпались в строчный поток. Всем
   блочным div прописан `display: block` (flex-правила перекрывают).
3. **Корень `body` всегда shrink-to-fit**, поэтому центрирование и кламп
   окна делает C++ (`clampShell`: left/top + width/height через SetProperty),
   а `#shell` — `position: absolute`. Внутри — колонка: фиксированный
   `#titlebar` и `#layout` с `flex-basis: 0px` (без него контент высотой
   больше окна схлопывал тайлбар в 0), контент — `display: block` +
   `overflow-y: auto`. `check_menu_rml.py` фиксирует все инварианты.
- тумблеры синхронизируются каждый кадр, слайдеры — круглым циклом
  параметр→DOM с допуском (значение пишется только при реальном изменении,
  поэтому запись не дерётся с перетаскиванием), показания и чипы цвета —
  только при изменении текста/цвета;
- кнопка «Настроить HUD» (вкладка HUD и панель Modules) запрашивает
  существующий HUD-редактор и прячет меню (латч как у закрытия);
- испытательные настройки катаны и короны живут в отдельном перетаскиваемом
  документе «Test tools (adapter)» (CSS `drag: drag`): он виден, только когда
  меню открыто и включена катана или корона, показывает статус, флаги,
  диагностические строки и ползунки; статус/диагностика обновляются только
  при изменении текста. Слайдеры катаны/короны дублируются во вкладке
  «Графика» и остаются согласованными через общий параметр;
- пока меню живо (первый успешный кадр отрисован), оно заменяет собой легаси
  click-GUI и старые тестовые панели. Любой сбой встраивания автоматически
  возвращает прежний интерфейс.

Ограничения (честно): ввод мыши в меню и в игру одновременно не различается
(как и раньше, курсор игровой мыши управляется флагом меню игры). Работа
в реальной игре не проверена — нужен тест пользователя.

## China Hat (test)

В игровом меню появилась отдельная перемещаемая панель **Visuals**, не новая
вкладка внутри закрытого ядра. Панель по оформлению приближена к Home/HUD;
она содержит включение эффектов и кнопки настроек `China Hat`, `Trail`, `Options`.
Кнопка настроек эффекта открывает справа настройки, слева — независимый
предпросмотр: для шляпы голова почти спереди, для следа персонаж сбоку с
демонстрационной лентой. При открытом редакторе эксперимент пытается найти
текстуру, используемую при отрисовке локального игрока: включите вид от третьего
лица. `Game texture N/N (verify)` — только кандидат, а не подтверждённый скин;
если показано несколько текстур, нажимайте `Next texture`. Пока подходящая
текстура не найдена, показывается примерный Стив. Текстуры остаются на GPU,
не сохраняются и не отправляются. Проверки в Minecraft пока не было; текстура
может не обнаружиться или оказаться не скином.

В окне Preview отдельно включается выключенный по умолчанию эксперимент
`Game model replay (test)`: пользователь подтвердил, что он показывает настоящую
игровую модель в подходящем виде от третьего лица. Повторяются только
поддерживаемые GPU draw-вызовы в отдельную прозрачную текстуру, не вызывается
повторно игровой renderer. Это не независимая камера: для показа модели пока нужно вручную включить F5
и выбрать подходящий ракурс. Экспериментальный перехват геттера перспективы
удалён: пользователь сообщил, что он мешал F5 и скрывал руку от первого лица.
После обновления пользователь сообщил, что ручное переключение F5 снова работает.
Возврат руки от первого лица ещё не подтверждён. Автоматическое переключение
пока не реализовано.

В редакторе China Hat включённая шляпа при обычном мировом проходе теперь
дополнительно повторяет свои уже существующие draw-вызовы в текстуру модели,
с прежними глубиной и прозрачностью; без активной шляпы или подходящего DSV
она может отсутствовать. При Old overlay копирование не гарантируется. Трейла
в GPU-preview пока нет. Само мировое перекрытие шляпы дальними блоками не
исправлено. Пользователь подтвердил, что реальная модель и шляпа появились в Preview,
но автоматическое переключение с первого лица не сработало. Надпись `Auto front
requested` означает лишь, что экспериментальный геттер возвращал значение,
а не что камера сменила вид. В новой версии перехват геттера удалён.
Для изучения настоящего переключения создан необязательный read-only скрипт
`DIAG_PREVIEW_CAMERA.ps1`: после проверки хеша он сохраняет небольшие фрагменты
кода из файла EXE, не читает память процесса или данные мира. Полученная
диагностика показала, что код камеры читает значение напрямую, минуя наш бывший
перехват геттера. Безопасная установка и восстановление перспективы не доказаны.
Повтор шляпы подтверждён на скриншоте; другие ракурсы и настройки требуют проверки. Режим
может повлиять на производительность или GPU-запросы игры; при артефактах,
сбоях или неверной камере снимите галочку и перезапустите игру. Проверки D3D
состояния не гарантируют безопасность. Текстура не читается на CPU и никуда
не отправляется.

Даже при успешном обнаружении скина это отдельная упрощённая модель, а не
полученная из игры модель персонажа: кости, нестандартная геометрия и настоящая
анимация не извлекаются. Материал может отличаться, а траектория трейла —
демонстрационная. Предпросмотр использует те же параметры, время, геометрию
шляпы и функцию bob, что игровой эффект; он виден даже когда модуль выключен.
Масштаб подбирается по максимальной высоте покачивания, а не каждый кадр:
голова не должна пульсировать, пока настройки не меняются. Исправление требует
проверки в игре. Цвет, прозрачность, размер и другие параметры меняются сразу. Пока редактор
открыт, клиентский HUD, уведомления и основное меню скрываются; `Back to menu`
возвращает их. HUD самой игры (например, чат) это не скрывает.
Оба эффекта по умолчанию выключены; их настройки действуют до закрытия игры
и пока не сохраняются. `Del` отключает эффекты и оверлей, но не выгружает DLL.

В `China Hat`: включение, заполнение, переливание или собственный цвет,
скорость цвета, радиус и высота конуса, вертикальный сдвиг и амплитуда/скорость
плавного покачивания. В `Trail`: включение, заполненная лента или линия,
переливание или свой цвет, скорость цвета, высота ленты и время жизни следа.
В `Options` можно отключить цвета. Переливание меняет общий цвет материала
во времени, не гарантирует градиент по отдельным вершинам. Пользователь ранее
подтвердил работающую привязку к своему игроку и окрашенные линии.

Когда эффект включают, заполнение и переливание для него включены по умолчанию;
их можно отключить до включения эффекта. Заполнение по-прежнему использует
неподтверждённый режим игровых треугольников: оно может не появиться,
привести к артефактам или вылету. Проверенные линии выводятся отдельно; при
проблемах отключите заполнение. Надпись `Fill: submitted` означает только вызов
рендера, а не гарантию видимой заливки. Пользователь сообщил, что в предыдущей
версии заливка работает; новая панель и её предпросмотр не проверены на Windows. Тестируйте в сохранённом или новом мире. Шляпа следует
за позицией/хитбоксом, а не за анимированной костью головы; корректное
перекрытие головой и стенами и прозрачность нового рендера требуют проверки.

Визуальные эффекты не используют прежнюю цепочку координат C, которая могла
указывать на другого игрока на сервере. Отдельный эксперимент координат может
по-прежнему использовать её.

Доступ только для пользовательского EXE с SHA-256
`2883b72a3579d95bfec73330c5e06f2463253b7ca530dd59f50885a71a724732` и
совпадающими PE-параметрами и машинным кодом. Если игра или доступ к EXE не
подходят, в меню написано `China Hat: unsupported game or unavailable`,
обычные функции остаются доступны. Совпадение кода не доказывает семантику
внутренних функций, ABI или правильность цепочки локального игрока. Отрисовка
пропускается при недоступных данных игрока, занятом tessellator и сомнительных
значениях; цвет шейдера сохраняется и восстанавливается. Исходный EXE не
изменяется. `Del` выключает и шляпу, и оверлей, но не выгружает DLL.
Подробности — в `research/china_hat/README.md`.

### Оформление HUD

Внутриигровые карточки существующего HUD оформлены в тёмном полупрозрачном
стиле с зелёной рамкой и цветным текстом по мотивам макета лаунчера. Это
адаптация, не буквальная копия: реальные виджеты остаются отдельными карточками
и используют существующие значения и расположение. Игровой HUD Minecraft
(жизни, хотбар и т. п.) не заменяется демонстрацией из макета.

В игровом меню окно `HUD` → `Open HUD editor` содержит переключатели доступных
виджетов, `Widget background opacity` и `HUD text color`, а также настройки
отдельной карточки `Module List HUD`. Масштаб и позиция списка задаются отдельно;
его пример отображается справа в редакторе. Прозрачность относится к фону и
рамке, не к тексту; старые тени/свечение и отдельные элементы отрисовки могут
оставаться видимыми. Для изменения размера/позиции других виджетов используются
существующие настройки клиента. Пока редактор открыт, остальной клиентский HUD
и уведомления скрыты; `Back to menu` или закрытие меню возвращает их.

Новые параметры оформления и Module List действуют только в текущем сеансе и
сбрасываются после выхода из игры. Переключатели штатных модулей остаются
привязаны к исходному клиенту. Возможен дубликат старого `Active Modules`.
Если подключение темы недоступно, сохраняется исходное оформление HUD. Новое
оформление и редактор необходимо проверить в Windows/Minecraft.

В Visuals есть `Opacity (test)` и `Options -> Vertex gradient (test)`.
Цвет вершин зависит от игрового материала; градиент не гарантирован. На скрине
пользователя после игрового прохода сущностей DSV был подключён и depth включён,
тогда как после экрана HUD depth выключен. Поэтому новая экспериментальная
отрисовка по умолчанию перенесена в конец прохода сущностей. Перехваты семи
методов Draw контекста D3D11 действуют только во время вызовов нашего tessDraw:
они требуют тот же DSV, включают проверку глубины без записи в неё, задают
blend и после каждого вызова восстанавливают прежние состояния. Непрозрачность
используется как blend factor. Пользователь подтвердил, что в предыдущей версии
эффекты скрываются за блоками и регулировка прозрачности работает. Игра может
менять матрицы или использовать другой путь рендера; перекрытие всеми типами
объектов, стабильность и новый предпросмотр требуют дальнейшей проверки. При недоступном контексте, DSV или перехватах
мировой рендер пропускается вместо автоматического старого экранного fallback.

По новым скриншотам пользователя при проверке глубины даже каркас шляпы
ошибочно скрывается далёкими блоками, а в `Old overlay` шляпа целая. Точная
причина ещё не установлена (возможны несогласованные матрицы/глубина или иной
этап рендера). Добавлен выключенный по умолчанию диагностический переключатель
`Hat at player pass (test)`: он пробует рисовать только шляпу сразу после
рендера локального игрока внутри прохода сущностей, с теми же обязательными
DSV/depth-проверками и прозрачностью. Трейл и старый экранный режим не меняются;
обычный мировой путь шляпы при включённом тесте не вызывается, так что двойной
отрисовки нет. Если подходящая глубина/хуки недоступны, шляпа не рисуется,
а не переводится в просвечивающий режим. Статус и тип сравнения глубины показаны
в Options. `submitted` не доказывает правильную глубину или безопасную работу.
Пользователь проверил этот альтернативный момент: шляпа оказалась разрезана
сильнее. Снимите галочку для возврата к прежнему мировому проходу; этот тест
не исправляет ошибку глубины.

В `Options` статус `World draw` сообщает о состоянии: `submitted` означает
только перехваченный GPU-вызов, не гарантию правильной картинки; `no depth`,
`hooks unavailable`, `blocked` и `no GPU draw` помогают диагностике. Переключатель
`Old overlay (see-through)` вручную возвращает предыдущий экранный путь, который
может просвечивать через игроков и блоки. `Del` отключает эффекты, но не снимает
установленные хуки до закрытия игры. Предварительно рекомендуется новый мир.

В `HUD → Open HUD editor` добавлены палитры Aogiri Green, Emerald, Graphite и
скругление карточек по новому макету; они влияют на реальные HUD-карточки,
а не на демонстрационные показатели. Это частичная адаптация, не полная копия
веб-макета; настройки пока действуют только в текущей сессии. Новые палитры и
скругление в игре ещё не проверены.

Файлы `HUD_ALL_IN_ONE.txt` и `HUD_PREVIEW.png` содержат описание/код и старый
условный макет HUD-плашки; PNG не является скриншотом нового предпросмотра.

Он ещё не проверен пользователем в Minecraft.

### Эксперимент мыши по Right Shift
Только для проверенного по SHA-256 x64 EXE 1.1.5 дополнительно проверяются
машинные инструкции очереди мыши и игрового input tick. При открытом меню
адаптер запрашивает игровое освобождение курсора и отбрасывает проверенные
мышиные события игровой очереди, не блокируя события UI. Ранее нажатые
игровые кнопки получают отпускание; после закрытия запрашивается прежний режим.
Пользователь подтвердил, что курсор и Right Shift работают, клики в меню не
передаются игре, а после закрытия управление восстанавливается. Если проблема

## Jump Rings — экспериментальный эффект прыжка

В панели `Visuals` включите **Jump rings (test)** и откройте её `Settings`.
У ног появляются расширяющиеся двойные кольца, вращающиеся сегменты,
полупрозрачные полосы-ореолы и поднимающиеся искры; всё плавно затухает.
Это геометрический ореол, а не проверенный эффект bloom. Доступны радиус, длительность,
прозрачность, цвет и радужный режим. По умолчанию эффект выключен, настройки
действуют только в текущем сеансе. Отключение оверлея через Delete отключает
и эффект.

Определение прыжка приблизительное: оно отслеживает подъём после спуска или
ровного движения локального игрока без ожидания стоянки на земле. Это не
проверенный игровой флаг прыжка. Поэтому возможны пропуски и срабатывания при подъёме по ступенькам,
в воде или при других вертикальных перемещениях. Эффект использует тот же
экспериментальный мировой рендер и проверку глубины, что и Trail; проблемы
перекрытия блоками или прозрачности ещё возможны. На Windows и в Minecraft
предыдущая версия эффекта работала у пользователя, но новый многослойный вид
ещё не проверен в игре, даже если отдельные тесты прошли.

## Пробный 3D-аксессуар — корона

`Visuals → 3D crown (test)` включает отдельную золотистую пробную корону из
встроенной объёмной геометрии. `Settings` меняет цвет, размер, высоту и
прозрачность; настройки действуют только в текущем сеансе, эффект выключен по
умолчанию. Он не заменяет игрока, China Hat или предметы и не загружает модели
из файлов. Через F5 вручную включите третье лицо, чтобы увидеть модель.

Аксессуар привязан к оценке положения головы локального игрока, остаётся
вертикальным и не учитывает поворот или анимацию головы. Данный пробный меш не
текстурирован. Используется прежний экспериментальный мировой проход и те же
ограничения глубины/цвета, что у других эффектов; итоговая видимость, цвет,
перекрытие блоками и положение должны проверяться в Minecraft. Сборка и тесты
не доказывают, что в конкретном кадре геометрия появилась на экране. Корона
не заменяет предметы; отдельный эксперимент с мечом описан ниже.

## Исследование замены алмазного меча на катану

Модель `assets/models/cyberpunk-katana.glb` скопирована без изменений из
предоставленного пользователем файла; автор и лицензия указаны в соседнем
`README.md`. Клиент **пока не загружает эту модель и не заменяет меч**.
Неизвестно, как в этой версии игры надёжно идентифицировать отрисовку именно
алмазного меча, сохранить руку и анимацию и преобразовать модель в координаты
предмета.

`DIAG_ITEM_RENDER.ps1` для исследования читает только файл проверенного EXE,
ищет строки и кандидаты RIP-relative LEA/MOV и сохраняет ограниченные окна
машинного кода в `ITEM_RENDER_DIAG.txt` на рабочем столе. Память процесса и
игровые файлы он не изменяет, сетевых запросов не делает. Найденные кандидаты
не являются подтверждёнными функциями рендера. Скрипт не запускался на Windows;
может не найти ни одного кандидата. Отчёт по желанию отправляется пользователем
вручную, без автоматической передачи.

Отчёт пользователя `ITEM_RENDER_DIAG.txt` выявил строку `diamond_sword` и
имена `ItemInHandRenderer` / `ItemRenderer`, но не установил безопасную точку
замены предмета. Выжимка адресов и ограничений — `research/item_render/observed.txt`.
`DIAG_ITEM_RENDER_2.ps1` исследует кандидатные x64 RTTI и таблицы виртуальных
методов в том же файле EXE и пишет `ITEM_RENDER_DIAG_2.txt`. Скрипт не пишет в
процесс, не изменяет игру и не делает сетевых запросов. Это всё ещё офлайн
анализ, Windows-исполнение скрипта и семантика найденных методов не проверены.

По второму отчёту найдено несколько вероятных путей подготовки предмета, но
виртуальный метод `0x59e870` оказался деструктором, не рендером. Исследование
по-прежнему не устанавливает безопасную точку замены. `DIAG_ITEM_RENDER_3.ps1`
собирает только три ограниченных окна кода проверенного EXE для анализа
конкретных кандидатов и сохраняет `ITEM_RENDER_DIAG_3.txt`. Его Windows-запуск
был выполнен пользователем. Текущий эксперимент в DLL описан ниже.

По `ITEM_RENDER_DIAG_3.txt` подтверждены дополнительные кандидатные цепочки,
но безопасная замена алмазного меча и система координат руки всё ещё не
определены; ниже описана последующая экспериментальная интеграция.

`tools/convert_katana.py` — офлайн-конвертер ограниченного подмножества GLB в
`GCM1`: геометрия, нормали и цвета материалов. Он проверен на предоставленной
катане; это не полный импортёр glTF. Он не поддерживает текстуры, анимацию,
скиннинг, сжатие, произвольный масштаб узлов или полный PBR/emissive-шейдинг.
`src/katana_mesh.h` проверяет бинарный формат перед отрисовкой экспериментальным
модулем. Исходная модель и условия
лицензии остаются в `assets/models/`. Проверка конвертации и чтения не доказывает,
что катану можно или удалось заменить в руке.

Для рендерера подготовлены два компонента:
`src/diamond_sword_candidate.h` — экспериментальная проверка по старому ID 276
и кандидатной таблице предметов (mock-тесты не доказывают идентификацию на 1.1.5);
`src/katana_geometry.h` — преобразование модели в цветные треугольники с
приблизительным центром хвата. Положение в руке не откалибровано. Компоненты подключены к экспериментальному
модулю ниже; поведение на реальной игре пока не проверено.

### Экспериментальная катана для алмазного меча

**Эта сборка — испытательная.** Работоспособность в игре не подтверждена:
в песочнице нет Windows и Minecraft, проверены только автоматические тесты.
Статус `Katana: visible; replacing sword` требует подтверждения пользователем
в обоих ракурсах.

Предыдущие версии не работали: собственный GPU draw выполнялся до настройки
предметного материала, не имел матрицы руки и подавлял оригинальный меч даже
при полностью невидимой катане (`D:1` не означал пиксели). Корневые причины
исправлены так:

1. **Отрисовка идёт только по доказанному пути.** Катана передаётся тем же
   tessellator-конвейером с `shaderColor`/`flag`, guarded `tessDraw` и
   восстановлением состояния, которым рисуются одобренные пользователем
   China Hat, Trail и Jump Rings — в мировом проходе с depth-тестом, пакетами
   по 2048 вершины. Собственная отправка `Draw` через контекст удалена.
2. **Положение и ориентация вычисляются из поворота игрока.** Углы читаются
   по четырём валидируемым источникам этого EXE (см. `src/katana_rotation.h`):
   слот игрока `ClientInstance+0x60` (доказан самим адаптером — по нему же
   работает China Hat; блок скорости из таблицы заканчивается ровно перед
   смещениями углов), две опубликованные цепочки CE-таблицы для той же версии
   (`[1921DF8]+18+58` и `[1921888]+10+58`) и хоп `+0x58` от наблюдаемого
   `ClientInstance`. Скрипт JetPack из той же таблицы доказывает, что значения
   в радианах, pitch положителен вверх, а направление взгляда —
   `(-sin, -cos)`; про обёрнутость yaw таблица молчит (её математика
   периодична), поэтому любой конечный yaw нормализуется в `[-pi, pi]`.
   Знак направления проверяется по фактическому движению игрока и
   переворачивается не более одного раза.
   Первое лицо: хват справа-снизу-спереди от камеры. Третье лицо: хват у правой
   руки игрока. Режим различается по расстоянию камера—глаза с гистерезисом.
   Масштаб/наклон/смещения настраиваются в меню (`Settings` у галочки катаны).
3. **Оригинал подавляется только при подтверждённой видимости замены.** Каждый
   пакет катаны обёрнут в D3D11 occlusion query; подавление включено лишь пока
   query насчитал реальные пиксели за последнюю секунду. Если катана не видна —
   рисуются обе модели, предмет никогда не пропадает. Любая ошибка query
   навсегда отключает подавление, оставляя оригинал.
4. **Идентификация предмета.** Первое лицо: внешний хук предметного рендера
   (проверка локального игрока + ID 276 + таблица предметов). Третье лицо:
   наблюдатель стриминг-вызова `0x5a22f0` и «отпечаток» текстуры из
   подтверждённого первого лица (для кэшированного вызова `0x59f200` по
   адресу возврата `0x56cd8e`); плюс мост длительностью 1 секунда после
   перехода F5, чтобы замена работала сразу после переключения вида.
   Наблюдатель никогда не пропускает оригинальный вызов. Другие предметы,
   другие игроки и инвентарь не затрагиваются (строгая проверка стека и
   область только собственного рендера игрока).

Диагностика в меню накапливается до выключения: `F` — совпадение кандидата
первого лица; `V` — ненулевой байт стека; `S` — идентификация меча в третьем
лице; `C` — вызов кэшированного рендера; `R` — углы прочитаны; `X` — цепочки
углов согласованы; `D` — мировая отрисовка выполнена; `O` — query подтвердил
пиксели; `P` — оригинал подавлялся. Флаги за сеанс, не за кадр.

Под ними четыре живые диагностические строки (пересчитываются при отрисовке
меню): `Rot P/A/B/H` — какой из четырёх источников углов сейчас жив
(P — слот игрока, A/B — глобальные цепочки, H — хоп `+0x58`), текущие
yaw/pitch и признак обёртки; `CI/PL/H58/iA/iB` — указатели ClientInstance,
игрока и промежуточных объектов; `Ang PL/H58/A/B` — сырые числа по смещениям
`+0xB8/+0xBC` на каждом кандидате (`--` — чтение недоступно) и признак
читаемого `Head+` (`+0x160`); `TP in/out/tex/learned` — сколько кэш-вызовов
третьего лица было внутри/вне области собственного рендера, какая текстура у
них в `+0x90` и какой отпечаток выучен из первого лица. Один скриншот этих
строк объясняет мёртвую цепочку без новой угаданной сборки.

Первый пользовательский тест (ветка `arena/0c7aa1e6-tets`, DLL `256b6fb8…`)
дал в первом лице `F V C = 1`, остальные флаги — 0: меч опознан и кэш-вызов
виден, но ни один источник углов тогда не прошёл валидацию. Текущая сборка
добавляет источник через слот игрока (не зависит от глобальных цепочек,
которые могли умереть в одиночной игре) и нормализацию неограниченного yaw;
если и это не оживит `R`, диагностические строки покажут, что реально лежит
в памяти.

Ограничения, о которых не заявляем лишнего: цвета — только baseColorFactor из
GLB (PBR/свечение не сохранены, конвертер их отбрасывает); катана не следует
анимациям взмаха (рендерер их не раскрывает) — только поворотам взгляда и
положению руки; в первом лице при упоре в стену катана может скрыться за
геометрией мира — тогда возвращается обычный меч. Хук камеры не используется;
F5, мышь, меню и остальные эффекты не изменены. Источник и условия модели —
`assets/models/README.md` и `THIRD_PARTY_NOTICES.txt`.

Никаких подтверждений работы на Windows/Minecraft у нас нет. Это опытный хук
приватных игровых функций: возможны неверный вид, положение или сбой игры.
Выключите галочку при проблеме; для полного отката DLL закройте игру и
установите предыдущую версию. Тестировать сначала в отдельном локальном мире.

## Новое меню на RmlUi (HTML/CSS) — миграция завершена

Пользовательский вердикт по встроенному ImGui-меню: функционально, но
внешне и архитектурно не нравится; нужен вид как у лаунчера (React +
WebView2). Rust + egui недоступен в среде сборки (тулчейн нельзя скачать:
серверы Rust заблокированы сетевым фильтром песочницы, бинарных зеркал на
GitHub нет). Выбран RmlUi 6.3: интерфейс описывается на настоящем HTML+CSS
(тот же язык дизайна, что у лаунчера), рендер нативный в D3D11 через
готовый `RenderInterface_DX11`, который принимает существующее устройство
игры и целевой render target, то есть встраивается в Present-путь точно
так же, как ImGui-оверлей.

Вендорено и проверено кросс-компилятором (192 файла коры RmlUi + DX11
рендерер, 19 файлов FreeType с минимальным набором модулей только для
TrueType/OpenType — см. `vendor/freetype-config/ftmodule.h`):
- `vendor/rmlui` — Include, Source/Core, Backends (только DX11-рендерер),
  MIT-лицензия;
- `vendor/freetype` — FreeType 2.13.3 (include + src), FreeType License.

Итог миграции: мост `src/menu_rml.cpp` с тем же публичным API, что был у
`menu_embed` (ввод из существующих хуков, очередь SetModule, теневые флаги
модулей, `ReplacesLegacyMenu`/`ConsumeHudEditorRequest`), дизайн в
`src/menu_rml_data.h`, сборка — `tools/build_adapter.py` (216 объектников,
единственный экспорт `GAYClientConnectWheel`), статические проверки —
`tests/check_menu_rml.py`. ImGui-меню удалено из сборки; заголовки
`vendor/imgui` остаются для типовой совместимости с легаси-оверлеем
(символы берутся из GAYClientCore.dll).
